# Security Model — REwebPortal

---

## 1. Threat Model

### Key Assets
| Asset | Sensitivity | Risk if Exposed |
|---|---|---|
| Buyer phone numbers | High | Harassment, spam calls |
| Agreement to Sale documents | Very High | Identity fraud, property disputes |
| Unit number associations | High | Buyer targeting |
| Grievance evidence files | High | Legal risk, privacy violation |
| Admin credentials | Critical | Platform takeover |

### Primary Threats
| Threat | Vector | Mitigation |
|---|---|---|
| **Account takeover** | OTP interception, brute force | OTP TTL 5min, max 3 attempts, bcrypt |
| **Data scraping** | Bulk API calls | Rate limiting, CAPTCHAon heavy pages |
| **Unauthorized doc access** | Direct R2 URL guessing | Presigned URLs, no public R2 access |
| **Defamatory posts** | Unmoderated forum | Moderation queue, report system |
| **SQL injection** | API inputs | Prisma parameterized queries (ORM) |
| **XSS** | Forum posts | Markdown → sanitized HTML (DOMPurify) |
| **CSRF** | State-changing requests | SameSite cookies + CSRF token on forms |
| **Admin impersonation** | Stolen JWT | Short JWT TTL (15min) + refresh rotation |

## 2. Authentication Security

### OTP Design
```
- 6-digit numeric OTP
- Generated using crypto.randomInt() (not Math.random())
- Stored as bcrypt hash in PostgreSQL (cost factor 10)
- TTL: 5 minutes
- Max attempts: 3 (then OTP invalidated, must re-request)
- Cooldown: 1 minute between resends, max 3 per 10 minutes
- Rate limiting by phone number + IP
- OTP record deleted after successful verification
```

### JWT Token Design
```
Access Token:
  - Algorithm: RS256 (asymmetric — private key on server only)
  - Payload: { sub: userId, role: UserRole, verificationStatus }
  - TTL: 15 minutes
  - NOT stored anywhere — validated on each request

Refresh Token:
  - Algorithm: RS256
  - TTL: 30 days
  - Stored in Redis with key: refresh:{userId}:{tokenId}
  - Redis entry deleted on logout → instant invalidation
  - Rotated on each use (refresh returns new refresh token)
  - Stored in httpOnly cookie (web) + Redis blacklist

Token Blacklist:
  - On logout: access token jti added to Redis blacklist (TTL = remaining access token lifetime)
  - On refresh: old refresh token invalidated immediately
```

### Session Management
```
- Login creates Redis entry: session:{userId} → last activity timestamp
- Admin force-logout: delete session entry + blacklist all tokens for user
- Automatic session expiry after 30 days inactivity
```

## 3. Data Privacy (DPDP Act 2023 Compliance)

### Personal Data Minimization
| What We Collect | Why | Retention |
|---|---|---|
| Phone number | Authentication (OTP login) | Account lifetime |
| Display name (first + last initial only) | Forum identity | Account lifetime |
| Unit number (hash only) | Ownership verification | Account lifetime |
| Agreement doc (encrypted) | Admin verification | Deleted after admin review + 30 days |
| Grievance description | Core feature | Until resolved + 2 years |

### What We Deliberately Do NOT Collect
- Full legal name
- Aadhaar or PAN number
- Full agreement to sale terms
- Precise unit number in plaintext (only SHA-256 hash for uniqueness check)
- Financial transaction details
- Loan information

### Anonymization Features
- Buyers can post grievances/forum posts as **anonymous** (shown as "Verified Buyer" publicly)
- Anonymous flag is stored but actual identity is in DB (accessible to admin for abuse prevention)
- Buyer can choose not to reveal which project they bought in — "I have a concern about this builder" mode

### Data Subject Rights (DPDP Act)
- **Right to access**: `GET /users/me` returns all personal data held
- **Right to correction**: `PATCH /users/me/profile`
- **Right to erasure**: `DELETE /users/me` — soft deletes account, anonymizes forum posts, deletes documents from R2 within 30 days
- **Right to withdraw consent**: Can revoke ownership verification, breaking the buyer-project link

## 4. File Storage Security

### Cloudflare R2 Configuration
```
- Bucket policy: Private (no public access)
- All objects server-side encrypted (AES-256, R2 managed keys)
- Object keys use CUID — non-guessable
- File access ONLY via presigned URLs generated by backend
  - Evidence files: presigned URL TTL = 15 minutes, ADMIN only
  - Builder logos/project images: presigned URL TTL = 24 hours (public-ish)
  - Agreement docs: presigned URL TTL = 5 minutes, ADMIN only

File Upload Flow:
  Browser → POST /grievances/:id/evidence → Backend validates
         ← Presigned upload URL (direct to R2, TTL 5 min)
  Browser → PUT <presigned-url> (direct upload, no server bandwidth)
  Browser → POST /grievances/:id/evidence/confirm → Backend records fileKey
```

### Evidence File Encryption (Additional Layer)
```
- Agreement to Sale documents additionally encrypted at application layer
- AES-256-GCM with key from environment variable (not in DB)
- Encryption key rotated annually; old key retained for decryption
```

## 5. API Security

### Input Validation
- All DTOs validated with `class-validator` + Zod schemas
- Markdown content in forum posts sanitized server-side before storage
- File upload: MIME type validated by magic bytes (not just extension)
- SQL: Prisma ORM uses parameterized queries exclusively

### HTTP Security Headers (via Helmet.js)
```
Content-Security-Policy: default-src 'self'; img-src 'self' data: cdn.cloudflare.com; ...
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Strict-Transport-Security: max-age=31536000; includeSubDomains
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

### CORS Configuration
```typescript
// Only allow requests from our own frontend domains
const allowedOrigins = [
  'https://rewebportal.in',
  'https://www.rewebportal.in',
  'https://staging.rewebportal.in',
  // Dev only:
  process.env.NODE_ENV === 'development' ? 'http://localhost:3000' : null,
].filter(Boolean);
```

### Rate Limiting (NestJS Throttler + Redis)
```
Limits defined per route group (see API Design doc)
X-RateLimit-Limit and X-RateLimit-Remaining headers on all responses
IP-based for public, user-based for authenticated
```

## 6. Content Moderation (Anti-Harassment)

### What We Allow
- Factual grievances with evidence
- Anonymous posting with platform identity verification
- Sharing RERA compliance data
- Community discussion about construction progress

### What We Prohibit (Platform Rules)
- Personal home addresses of builder employees
- Unverified financial fraud allegations without evidence
- Coordinated harassment campaigns
- Off-topic political content

### Moderation Workflow
```
New post/thread → Auto-flagged if keywords match abuse list
                → Visible immediately (trust by default for verified buyers)
                → Community "Report" button → MODERATOR queue
                → Moderator reviews → Hide / Allow / Escalate to Admin
                → Admin can permanently delete + warn user
                → 3 warnings → account suspended
```

### Defamation Protection
```
- All public-facing text describes facts + patterns, not defamatory opinions
- Grievance descriptions are private (admin/owner only) until escalated
- Aggregated stats (e.g., "67 complaints in this category") shown publicly, not raw complaint text
- Builder can submit official response to aggregated complaint stats (shown alongside)
```

## 7. Admin Security

### Access Control
```
ADMIN role:
  - Separate login (email + password, not OTP)
  - Password: bcrypt(cost=12), minimum 12 characters, complexity required
  - Admin accounts provisioned manually, no self-registration
  - All admin actions logged in admin_actions table
  - Failed logins: lockout after 5 attempts for 30 minutes

MODERATOR role:
  - Same as buyer auth (OTP) + role elevation by admin
  - Limited to moderation endpoints only
```

### Admin Audit Log
Every admin action records: who, what, when, which entity, what changed. Audit log is **immutable** (no DELETE on admin_actions table, enforced at DB level via trigger).

## 8. Infrastructure Security

### Environment Variables
```
- All secrets in environment variables (never in code)
- Production secrets in Railway/Vercel secret managers
- Separate credentials per environment (dev/staging/prod)
- DB credentials rotated on any team member departure
- JWT private keys are RSA-2048, stored in secrets manager
```

### Database Security
```
- Supabase: connection via SSL required
- PgBouncer: connection pooling limits blast radius
- DB user for API: limited privileges (no DROP, no TRUNCATE)
- DB user for migrations: separate, higher privileges, not running in production app
- Supabase RLS enabled as additional layer
```

### Dependency Security
```
- Dependabot enabled on GitHub for auto-PR on security patches
- npm audit run in CI pipeline; fails build on HIGH+ severity
- No direct eval() or dynamic require() patterns
- Lockfile (pnpm-lock.yaml) committed to repo
```
